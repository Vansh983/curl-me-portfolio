#### P04. Disposable software

Date: 2d at capture (2026-10-25); exact publication date unavailable

Found in: [local session capture](/Users/vsood/.claude/projects/-Users-vsood-work-curl-me-portfolio/b7e8111f-ae0d-4392-b62c-959469ab4af9.jsonl:499), captured 2026-10-25T05:09:49.312Z; post. Page: [Vansh's activity](https://www.linkedin.com/in/vanshsood/recent-activity/all/).

The earlier capture also labels this “12h” on 2026-10-22 (session 272a57d2, line 314). A public permalink was found, but no usable dated post metadata was returned: [LinkedIn post](https://www.linkedin.com/posts/vanshsood_i-dont-know-if-this-is-a-controversial-take-activity-7518935559944228864-E9at).

```text
I don’t know if this is a controversial take or not, but something I’ve been seeing over the past few months is that our team is constantly adopting disposable software internally.

Our internal automations and tooling have increasingly been moving in that direction. By disposable software, I mean agents or small pieces of code that we use for a specific job, without expecting that version to stick around forever.

Small Slack bots, internal ticketing tools, customer ops workflows, certain scrapers and bots for news etc. Some of these can be replaced within minutes when what we need changes.

I was watching Max Kanat-Alexander talk on code quality, and his distinction between disposable and durable software felt very similar to what we’ve been doing. That’s what got me to start writing this.

The interesting part is who’s building them as well. Engineers are writing code. Our operations team and GTM engineers are building on top of no-code tools, including our own platform. People are making the software they need to do their jobs.

For years as developers, so much of what we’ve been taught and talked about has been maintainability. If someone has to live with this code for years, it needs to be maintainable.

But I’m finding myself asking that question differently for these smaller tools. How long do we actually need this version? Is maintaining it worth more than rebuilding it when the workflow changes?

The cost of building hasn’t literally gone to zero, but it’s dropped enough to change those decisions for us.

That makes the durable platform underneath even more important to me. The infrastructure, data, and reliability still need long-term care. Having that foundation is what lets the tools on top be replaceable.

I still care a lot about building software that lasts. I’m just getting more deliberate about which parts need to.

Very curious to see how these disposable pieces end up becoming self healing durable software.
```

The Multisite feature enables us to create multiple websites using the same root directory or the same code base. These websites are linked to one drupal folder containing the files and folders of all the websites we create. Due to this all the websites we create get linked with each other while having different structures and different content. For example, if we install a module in one of the websites, we could enable it in another linked website as the module folder will be created in the drupal folder both the websites are linked to. The websites we create are different because they have different databases while having a common code base.

It has five content nodes, each for a football club, a home page and a view containing the nodes.



Steps:


Create subdomains for the websites you want to create. Example; footballclub, wonders.
Create two different MySQL servers for these two subdomains and assign them two different users.
Upload the drupal core installation zipped file onto your along with the subdomain folders and extract it to a folder and rename it. Example: Drupal.
Create two new folders namely, footballclub and wonders in drupal/sites/.  Now copy files default.services.yml and default.settings.php from drupal/sites/default  to drupal/sites/wonders  and  drupal/sites/footballclub  as services.yml and settings.php respectively.

Install drupal in both of the subdomains using the servers created in Step 2.
